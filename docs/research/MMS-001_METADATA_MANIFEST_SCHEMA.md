# MMS-001 Metadata Manifest Schema

Version: 1.0.0

Status: Draft — Approval required; generation not authorized

Architecture Baseline: ABR-1.0 (Frozen)

## Manifest Purpose

This contract defines the metadata manifest required for every future dataset, experiment, replay, model, evaluation, or accepted artifact in the `CONTROLLED_RESEARCH_REGENERATION` track. It provides auditable identity, provenance, validation, acceptance, and reproducibility evidence without modifying historical contracts.

## Identity

Required identity fields are Research Track ID, Dataset ID, Dataset Version, Schema Version, Lifecycle State, Run ID, and Manifest ID. Related Experiment, Replay, Model, Evaluation, Feature Set, Label Set, and Data Snapshot identities must be recorded when applicable.

## Source Provenance

Record Source ID, source location, provider, symbol, timeframe, coverage range, source timezone, normalized timezone, source format, source schema version, acquisition method, acquisition configuration, source byte size where available, source record count, and source SHA-256 after authorized validation.

## Transformation Provenance

Record generator path, generator Git commit, generator hash where applicable, configuration path and hash, ordered transformation steps, random seed where applicable, operating environment identity, commands, exit codes, and start/completion timestamps.

## Feature Provenance

Record Feature Set ID and version, feature configuration and hash, input requirements, timeframe, causality, lookback and warm-up, fitting partition, normalization policy, and missing-value policy.

## Label Provenance

Record Label Set ID and version, target definition, barrier and timeout rules, collision policy, causal timing, required future path, partition restrictions, and outcome-imputation policy.

## Partition Provenance

Record partition identity and version, start time, end-exclusive time, record count, partition hash, purge or embargo parameters, seal status, and access status. Train, Validation, and Test records must be represented separately.

## Validation Evidence

Record validator identity and version, validation report location, input identities and hashes, validation status, failed checks, warning checks, exit status, and validation timestamp.

## Acceptance Evidence

Record approval state, approving role, approval timestamp, acceptance report, accepted-storage location, freeze timestamp, immutable-storage status, and independent-backup status.

## Required Fields

The fields defined in Identity, Source Provenance, Transformation Provenance, Partition Provenance, Validation Evidence, and Acceptance Evidence are mandatory for the applicable object. Missing mandatory fields fail closed.

## Optional Fields

Provider-specific identifiers, comments, non-output-affecting diagnostics, and supplementary evidence may be added only when clearly marked optional and version-compatible. Optional fields must not replace required provenance.

## Fail-Closed Rules

The manifest is invalid when identity is ambiguous, source or configuration provenance is incomplete, hashes are unavailable after required validation, partition boundaries conflict, Validation/Test access is unrecorded, or acceptance and freeze evidence is missing. No artifact may be accepted from an invalid manifest.

## Manifest Versioning

Manifest changes use an explicit schema version. A breaking field, semantic, serialization, or identity change requires a new major version and review. Existing manifests are immutable; corrections create a new manifest linked to the superseded record.
